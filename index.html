Agents are replaceable.
Governance isn’t.

A concise architecture read of CopilotKit/OpenBot: an on-premises agent workspace that places an AG-UI adapter, tool governance, audit, and Bot computers around interchangeable agent runtimes.

Repository CopilotKit/openbot ↗ Protocol AG-UI Project status Alpha template Scope Docs + selected source files
Core thesis

OpenBot’s central design is a server-owned control plane around agents—not a new agent framework. Agent roles, tool grants, approval rules, execution policy, and audit are separate parts of the system.[1][2]

01 / System shape

The platform owns the boundaries

The model reasons inside an endpoint. The server resolves identity, thread, capabilities, and whether a requested action is permitted.

02 / Agent patterns

Five decisions worth borrowing

These patterns make agent behavior inspectable and bounded, while allowing the underlying framework to change.

PATTERN 01INTEROPERABILITY

Protocol boundary, not framework lock-in

Any AG-UI-compatible endpoint can join. OpenBot stores the coworker’s durable profile and role separately from its runtime endpoint; new agents do not require a new front end.[1][2]

PATTERN 02LEAST PRIVILEGE

Job description ≠ capability grant

The standing role tells the agent what job it has. Separate grants decide which MCP tools, components, and skills it can use; an action policy then decides whether a particular operation may execute.[2][4]

PATTERN 03GOVERNED TOOLS

Mediate actions at the server

For browser actions, the gateway resolves element references against a server-held snapshot, evaluates policy, records the decision, and only then forwards the action. This avoids trusting labels supplied by the model.[3][4]

PATTERN 04COORDINATION

Typed handoffs + durable delivery

A handoff names the task, constraints, and expected answer. The server signs the run context and delivers work through a leased queue with retry and recursion limits, rather than relying on a fragile in-memory callback.[5][6]

PATTERN 05CONTROLLED EVOLUTION

Learning is evidence → review → delivery

Conversation evidence can feed an Intelligence Learning container. The system proposes skills, but publication is a review step; the resulting instructions do not silently create new tool permissions.[8]

PATTERN 06UNATTENDED WORK

Schedules are worker jobs, not API timers

Routines are owner-scoped scheduled instructions. A separate worker or CronJob sweeps due work, and the shared queue coordinates claims across replicas.[1][7][10]

03 / Production caveats

What the architecture does not guarantee

Several safeguards depend on deployment configuration or an extra process. Treat these as rollout checks, not footnotes.

! Verify before production

Policy engine fails closed; shipped default is permissive

The policy evaluator denies on missing or malformed rules, but the documented startup policy is explicitly allow: ["true"] unless an environment or saved administrator policy replaces it. Configure and verify the intended policy before exposing tools.[1][4]

Per-Bot browser isolation is conditional

With the supervisor configured, each Bot gets its own computer, workspace volume, and browser profile. Without it, Bots share the configured computer and browser state.[1][10]

Routines need a scheduler process

The API stores routines but does not fire them by itself. The documented one-container image requires an external cron or scheduled job; an unstarted worker means no routine runs.[7][10]

Current browser actions are user-session driven

The architecture describes browser computer tools as actions executed by the person’s session; current headless runs cannot drive that computer. Do not assume unattended schedules can perform browser automation.[1]

Learning depends on an external service and review

Evidence collection and skill delivery require an assigned CopilotKit Intelligence container. Candidate analysis does not auto-publish a skill, and bring-your-own remote agents must consume the forwarded skill context.[8]

It is a template in alpha

The repository labels itself an alpha, actively developed template—not a hosted service or finished product. Expect integration work and rough edges.[9]

Bottom line

Best idea to reuse: let the model propose intent, but keep permissions, policy decisions, identity, and audit in a trusted server layer. Make delegation typed and durable rather than prompt-only.

Most important caveat: “fail-closed engine” is not the same as “deny-by-default deployment”—OpenBot documents a permissive shipped startup rule. Review that policy alongside computer isolation and worker setup before adopting the template.[1][4][10]
